# Data Model: Vault Export

This design does not add a persistent `VaultExport` table. A generated export is
an ephemeral representation of a single read snapshot and exists only for the
duration of the response.

## Existing source entities

### Vault / `vault.Document`

- `id`: stable document identifier.
- `title`: document title.
- `notes`: user-entered notes.
- `expiry_date`: nullable ISO date.
- `reminder_sent_at`: nullable UTC ISO-8601 timestamp.
- `created_at`, `updated_at`: UTC ISO-8601 timestamps.
- `owner_id`: authenticated owner identifier.
- `category`, `subject`, `document_type`: related taxonomy `id` and `name`.

Only rows whose `owner_id` equals the authenticated requester are eligible.
The current model has no file attachment; the package must not claim to export
one. Related taxonomy descriptions/timestamps and unrelated account tables are
also outside the approved field inventory.

## Ephemeral Vault Export

- `format`: `vault-export`.
- `schema_version`: integer `1`.
- `created_at`: UTC package creation timestamp.
- `snapshot_at`: UTC timestamp at the start of the consistent read snapshot.
- `owner`: safe identifying metadata (`id`, `email`, `display_name`) from the
  authenticated user.
- `document_count`: number of serialized documents, including zero.
- `attachments`: boolean `false` for this version.
- `files`: member name, byte length, and SHA-256 digest for package members.
- final archive digest: calculated for validation/diagnostics and optionally
  exposed as a response header; it is not an authorization mechanism.

## State transitions

The export is not published until it passes all states:

`not started` → `snapshot materialized` → `members serialized` → `archive
closed` → `validated` → `download response`.

Any serialization, size-limit, ZIP, or validation error transitions to
`failed`; no attachment response is returned. A network interruption may leave
the client with an incomplete transfer, but the server never labels an
unfinalized archive as ready and supplies a content length.

## Validation rules

1. Authentication is required for generation.
2. Owner filtering occurs in the ORM query.
3. Empty querysets produce `documents.json` as an empty array and
   `document_count: 0`.
4. Manifest count and member hashes must match the generated members.
5. The archive must close successfully and pass ZIP readability checks before
   the response is constructed.
6. A configured maximum record/byte bound must fail clearly rather than
   truncate.
7. No generated bytes are persisted in the database, filesystem, logs, or
   declared security-zone paths.
